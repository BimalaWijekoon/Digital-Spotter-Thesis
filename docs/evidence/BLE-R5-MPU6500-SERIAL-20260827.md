# BLE R5 — MPU6500 serial bring-up evidence

**Result:** PASS
**Date:** 2026-08-27
**Environment:** real ESP32-C3, MPU6500, Raspberry Pi 4B, and owner-applied gentle movement

R5 started from the frozen passing R4 source. It added only independent I2C
initialization and raw sensor sampling. BLE still sends deterministic synthetic
R4 fields and remains unpaired/unencrypted.

## Hardware contract proved

```text
SDA: GPIO 5
SCL: GPIO 6
I2C: 100 kHz
address: 0x68
WHO_AM_I: 0x70 exact
rate: 50 Hz
accel range: +/-2 g
gyro range: +/-250 degrees/s
DLPF: 3
```

The complete boot and 200-sample logs are in
`firmware/esp32_c3_research/checkpoints/r5/`. The independent validator passed
exact identity/address, continuous capture indices, monotonic sample counters,
all-six-axis movement, signed-16-bit bounds, and zero terminal/consecutive I2C
errors. One initial bus transaction failed and recovered through one bounded
retry; no persistent failure followed.

## BLE non-regression

After Serial validation, the Pi received 403 exact 20-byte synthetic packets at
50.266276 Hz with 20,000 us device timestamp increments, zero sequence gaps,
zero invalid lengths, and zero disconnects. The separate GATT roles and bounded
control echo also passed.

## Boundary

This proves the sensor is connected, is exactly an MPU6500, and produces changing
raw values. It does not yet put those values on BLE. R6 is the only authorized
next stage and will replace just the six synthetic fields while preserving the
proven transport.
