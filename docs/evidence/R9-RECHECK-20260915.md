## Recovery discrepancy and next diagnostic

Reconnect run task completion sequence (excluding final stop):

```text
GATT contract verified
connection task completed: r9-notification-processor,r9-status-poller
GATT contract verified
connection task completed: r9-disconnect-waiter
GATT contract verified
```

BlueZ journal showed four `No matching connection for device` entries in the
test interval. The queried kernel journal interval had no entries. This does
not establish an over-air failure reason.

Code inspection identifies a **possible Pi-side lifecycle race**, not a proven
ESP defect: the bench directly awaits `runtime.transport.disconnect()` while
runtime cleanup can also call that method. `disconnect()` clears `_client`
before awaiting the backend and sets a shared disconnect event afterward.
An old delayed completion could therefore signal a subsequent connection.
The runtime's notification consumer also exits when `is_connected` becomes
false; the drop counter records bounded queue overflow, not proven radio loss.
These mechanisms warrant a deterministic interleaving test before firmware or
radio changes. No fix or root-cause confirmation is claimed here.
